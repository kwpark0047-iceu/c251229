# 주요 문제 보완: DB 검증 누락과 빌드 경계

## 수정

- 기존 CI 격리 DB 명령은 database.test.ts만 포함해 신규 회원 보관 9건을 누락했다. member-archive.test.ts와 JSON 결과 게이트를 추가했다.
- 결과 게이트는 두 필수 파일(최소 11건+9건), 전체 성공, 실패/보류/건너뜀 0건을 요구한다. 파일 누락·중복·실패한 훅·빈 보고서도 차단한다.
- 로컬 release-safety 검증도 테스트 JSON에 같은 게이트를 적용하며, 통과하지 않으면 verified=true를 반환하지 않는다. 고정된 과거 릴리스에 신규 테스트가 없다면 차단되는 것이 의도된 동작이다. 누락을 우회하려고 기준선을 바꾸거나 테스트를 복제하지 않는다.
- CI는 type-check → lint → test/isolated-db 순서로 실행하고 DB 확인 후 브라우저 검증을 수행한다.
- Turbopack 루트를 npm 명령이 실행되는 체크아웃으로 명시해 상위 폴더의 lockfile 자동 선택을 방지한다. Next 명령은 해당 체크아웃에서 실행해야 한다.

## 검증

- 게이트/워크플로의 누락 재현 후 보완했으며 도구 회귀 테스트 41건이 통과했다.
- 로컬 결과 파일에도 db-gate 실패와 verified=false를 명시해 Vitest 종료 코드 0만 보고 승인하지 못하도록 했다.
- 실제 Vitest 실행에서 DB 20건 건너뜀/종료 코드 0 → 게이트 종료 코드 1을 확인했다. 이는 차단 동작 검증이며 DB 실검증 성공이 아니다.
- 빌드 루트와 CI 계약 관련 Vitest 5건 통과.
- 최종 순차 결과는 `.local-state/release-20261022/validation-gaps-results.json`에 기록하며 databaseVerified=false는 실제 DB 검증 전까지 유지한다.
- 최종 type-check → lint → test → build 모두 종료 코드 0. Vitest 523건 통과/DB 20건 건너뜀이며, 실제 GitHub Actions 실행이나 DB 통과를 의미하지 않는다.
- 최종 빌드 로그에서 상위 lockfile 루트 추정 경고는 발생하지 않았다. 배포 대상 소스 해시는 `bbbb11b4fdfb1f9f3135a2272820319831b1e3348c6125b2f9a9979fe9c72bf8`이다.

## Docker 진단 및 범위

- 공간 확보 후에도 엔진 버전/격리 컨테이너 상태 요청이 각각 10초 시간 초과였다.
- WSL 목록은 Ubuntu와 docker-desktop이 Running임을 반환했다. 실행 중 표시만으로 엔진 정상 동작을 의미하지 않는다.
- Docker 로그에 2026-10-21 디스크 input/output error 및 containerd 소켓 연결 거부가 남아 있다. 현재 파일시스템 손상 여부나 장애 원인을 확정하는 증거는 아니다.
- 사용자가 승인한 정상 Desktop 재시작을 90초 제한으로 시도했지만 프로세스가 종료되지 않아 실패했다. 강제 재기동은 별도 승인 대상이다.
- 이후 별도 승인을 받아 Docker 설치 경로의 전용 프로세스만 종료하고 `wsl --terminate docker-desktop`을 실행했다. 전용 배포판 종료는 성공했으며 Desktop을 다시 시작했다. 제한된 엔진 준비 확인은 시간 초과였다.
- 재기동 직후 Ubuntu는 Running이었지만 최종 조회에서는 Ubuntu와 docker-desktop 모두 Stopped였다. Ubuntu/전체 WSL 종료 명령은 실행하지 않았으며 상태 변경 원인은 미확인이다. 추가 복구 조작을 중단하고 사용자에게 외부 종료 여부를 질문했다. DB 테스트는 여전히 미실행이다.
- 이후 사용자가 Ubuntu/WSL을 직접 종료했다고 확인했다. 해당 Stopped 상태를 원인 불명의 장애로 판단하지 않는다. 재확인 시 Desktop Backend IPC가 없었고 정상 시작 명령도 제한 시간 내 완료되지 않았다. Ubuntu를 임의로 재시작하지 않았으며 사용자에게 Desktop 화면의 시작 차단 안내를 확인 요청했다.
- 볼륨 삭제, 공장 초기화, 파일시스템 수리, Ubuntu/전체 WSL 종료, 운영 DB/계정 변경, 실제 메일, 배포는 수행하지 않았다. 예약 작업은 0건을 유지한다.

## 남은 조건

Docker 복구 → 전용 컨테이너/포트 신원 검증 → 합성 스키마 DB 20건 실행 → 게이트 통과 → 별도 운영 스키마/배포 승인 순서가 필요하다. Git의 기존 변경과 과거 릴리스 기준선은 보존했으며 최신 운영 기준선으로 승격하지 않았다.
