# 경기데이터드림 Bad Request 점검

## 직접 확인한 사실

- 로컬 경기 API 키로 의원(AsembyStus), 병원(GgHosptlM), 일반음식점(GENRESTRT), 푸드트럭(Resrestrtfodtuck), 전문대학(Jnclluniv)을 각 1건 조회해 HTTP 200 및 레코드를 확인했다. 키·업소 데이터는 출력하거나 저장하지 않았다.
- 의원 1,000건 조회 후 기존 코드와 같은 관리번호 500개로 중복 조회 쿼리를 계산하면 인코딩된 쿼리만 41,639바이트였다. DB 요청은 실행하지 않았다.
- 실제 Supabase 클라이언트와 가짜 fetch를 사용해 긴 URL을 HTTP 400으로 거절하는 조건에서 기존 코드가 `Bad Request`를 반환하는 것을 재현했다.
- 이는 코드의 확정된 크기 제한 결함이다. 사용자가 본 개별 운영 실패의 요청·서버 로그를 대조하지 않았으므로 모든 운영 Bad Request가 동일 원인이라고 단정하지 않는다.

## 수정

- 고정 500개 단위뿐 아니라 URL 인코딩 크기를 기준으로 중복 확인 요청을 분할한다.
- 필터 예산을 4,000바이트로 제한하고 기본 URL·기타 파라미터 여유를 둔다. 반복 관리번호는 조회 단계에서 중복 제거한다.
- 관리번호 하나가 제한을 넘으면 쓰기 전에 중단한다. 기존 관리번호 생성 규칙, 조직 RLS, 기존 영업 상태 유지 규칙 및 DB 스키마는 바꾸지 않는다.
- 새 회귀 테스트 2건은 수정 전 모두 실패했고 수정 후 모두 통과했다. 기존 동기화 관련 테스트를 포함하면 11건 통과했다.

## 별도 원본 제약

- 대학교 `Univ`는 키 없는 직접 조회에서도 `ERROR-310`을 반환했다. 임의로 사용 중지를 해제하지 않는다.
- 커피숍 후보 `RESRESTRT`의 실제 샘플 필드 목록에 `BIZPLC_NM`이 없다. 업종명을 업소명으로 저장하면 허위 리드·잘못된 중복 병합 위험이 있어 비활성화를 유지한다. 업소명이 포함된 대체 데이터셋의 계약 확인 후 전환해야 한다.

## 검증 및 운영 안전

- 순차 검증 로그: `.local-state/release-20261022/gg-fix-{type-check,lint,test,build}.log`.
- 단계별 성공 여부: `.local-state/release-20261022/gg-fix-results.json`.
- 실제 운영 DB 연결·저장·마이그레이션·회원 변경·동기화 실행은 하지 않았다. 예약 작업은 `crons: []`를 유지한다.
- DB 실연동 테스트와 운영 배포는 별도 작업이다. 모의 테스트의 통과만으로 운영 저장 성공을 보장하지 않는다.
- 이번 순차 실행은 type-check, lint, test, build 모두 종료 코드 0으로 통과했다. 테스트 466건 통과, 격리 DB 11건 건너뜀이다.
